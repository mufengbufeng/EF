# 敌人击败积分与 UI 同步设计

## 背景

现有实现中：
- `EnemyEntity` 已有完整受击与死亡流程。
- `GamePlayModel` 已支持 `CurrentScore`、`SetScore`、`AddScore`。
- `GamePlayController` 已订阅模型属性变化并刷新 `GamePlayView`/`GameMenuView`。

缺口是“击败事件未写入积分模型”，导致界面分数不随战斗变化。

## 目标

1. 在敌人死亡时可靠地增加玩法积分。
2. 将积分变化通过现有 Controller 刷新链路实时反映到玩法 UI。
3. 保证方案简单、可维护，不引入额外系统复杂度。

## 非目标

1. 不引入事件总线化的战斗结算系统。
2. 不扩展多种计分规则（连杀、倍率、敌人类型权重）。
3. 不重构现有 UI 框架结构。

## 决策

### 决策 1：在 `EnemyEntity` 死亡判定点直接结算积分

- 方案：在 `TakeDamage` 判定生命值归零且进入 `Dead` 状态时调用 `GamePlayModel.AddScore(1)`。
- 原因：该位置最接近“有效击败”的事实来源，且已有 `_isDead` 防重入保护。
- 取舍：相比引入统一战斗事件系统，耦合更高，但首版成本最低、可读性最好。

### 决策 2：复用 `GamePlayController` 现有模型订阅刷新链路

- 方案：保持 `PropertyChanged(CurrentScore)` -> `RefreshScore` -> `GamePlayView.UpdateScore` 的路径。
- 原因：项目已有稳定链路，避免新增轮询或重复订阅。
- 取舍：需要确保积分文本文案在 `GamePlayView`（及可选的 `GameMenuView`）统一。

### 决策 3：计分规则固定为每击败 +1

- 方案：首版使用固定常量，后续若有策划需求再配置化。
- 原因：用户需求仅要求“击败敌人增加积分”，固定值最符合最小实现原则。
- 取舍：灵活性有限，但可在后续独立变更中低风险扩展。

## 关键约束

1. 同一敌人实例最多结算一次积分。
2. 仅“被玩家击败”计分；越界回收、流程清理不计分。
3. UI 仅消费 `GamePlayModel`，不直接读取敌人状态，保持单一数据源。

## 风险与缓解

1. 风险：死亡路径被重复触发导致重复加分。  
缓解：依赖 `EnemyEntity._isDead` 与状态切换顺序，在进入死亡分支后立即阻断后续判定。

2. 风险：UI 文案或默认文本不一致，造成体验割裂。  
缓解：在工作阶段统一 `GamePlayView`（必要时 `GameMenuView`）积分文案，并补充手工验证项。

3. 风险：后续需要差异化奖励时当前固定值不够用。  
缓解：将“固定 +1”作为显式约束写入规格，后续以独立变更做配置化。
