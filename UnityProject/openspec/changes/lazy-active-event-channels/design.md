## Context

当前 `EventHub.Generated.cs` 为每个 `[EventArgs]` 类型生成一个立即初始化的属性：`public EventChannel<T> XxxEvent { get; } = new();`，并在构造函数中把所有实例放进 `_allChannels`，随后在 `Update()` 中每帧无条件遍历并调用 `Flush()`。

这种结构有两个直接结果：

1. `EventHub` 构造成本与事件类型数量线性相关。即使某个事件在整局游戏中从未使用，也会预先分配 handler 数组和 ring buffer。
2. 异步刷新成本与声明的 Channel 数量线性相关。即使没有任何入队事件，也需要每帧扫描全部 Channel。

项目当前事件量不大，但 `zero-gc-event-system` 已经把事件系统定位为框架级基础设施，后续事件类型继续增长是大概率事件。因此需要把 Channel 生命周期和调度方式从“全量常驻”改成“按需存在、按需工作”。

约束条件：

- `EF.Runtime` 是 AOT 层，事件基础设施必须保留在该层；生成代码仍位于 `GameLogic` 热更新层。
- 业务侧已采用 `EventHub.XxxEvent.Publish/Enqueue/Subscribe` 调用方式，优先保持 API 形态稳定。
- Unity 主线程模型不变，本次设计不引入线程安全要求。
- 现有 Editor 监视面板依赖 `IEventChannelInfo` 读取状态，设计需要继续支持调试可视性。

## Goals / Non-Goals

**Goals:**
- 将 `EventHub` 的 Channel 创建改为按需发生，而不是启动时全量初始化。
- 将异步队列刷新改为仅处理活跃 Channel，而不是每帧遍历所有声明的 Channel。
- 保持现有业务层的类型化事件访问方式基本不变，避免大规模迁移调用点。
- 保留对 Channel 调试信息的可观察性，使 Editor 面板能区分“未创建”“已创建但空闲”“活跃”状态。
- 让同步 `Publish` 与异步 `Enqueue` 的运行时成本路径更明确，避免同步事件承担异步调度负担。

**Non-Goals:**
- 不重新设计 `[EventArgs]`、`EventChannel<T>` 的类型化事件模型。
- 不引入跨线程发布、锁、无锁队列等并发机制。
- 不改变业务侧事件名称、事件结构体定义方式或 `EventHub` 的对外命名。
- 不把所有调试逻辑搬到运行时常驻对象池或单独监控服务中。

## Decisions

### D1: 生成的 `EventHub` 改为“描述符 + 延迟实例化”结构

**选择**：对每个事件生成私有 backing field 和公共属性访问器，属性首次访问时才创建 `EventChannel<T>` 实例。`EventHub` 不再在构造函数中直接 `new` 全部 Channel。

**理由**：
- 直接消除“未使用事件也预分配数组”的启动浪费。
- 对业务侧 API 最友好，调用方仍通过 `EventHub.XxxEvent` 访问，不需要改调用形式。
- 生成代码即可表达这一模式，不需要为每个事件维护反射字典。

**替代方案**：
- 使用 `Lazy<EventChannel<T>>`：会引入额外包装对象，并使调试/状态控制更绕。
- 用 `Dictionary<Type, IEventChannel>` 做统一懒加载：会把类型化访问退化成查表路径，且不如生成属性直接。

### D2: `EventHub` 维护“活跃异步 Channel”集合，而不是全量 `_allChannels`

**选择**：只把存在待刷新的 Channel 放进活跃集合；`Update()` 只遍历该集合。Channel 队列从空变非空时加入，队列清空后移除。

**理由**：
- 直接消除空闲帧对所有 Channel 的扫描。
- 成本与“当前有多少异步事件待处理”相关，而不是与“声明了多少事件类型”相关。
- 与当前 `Enqueue/Flush` 模型兼容，不需要改业务语义。

**替代方案**：
- 继续维护“所有已创建 Channel”列表，然后在 `Update` 中检查 `PendingCount > 0`：虽然比全量声明好，但仍会让已创建的同步 Channel 参与空转扫描。
- 改成全局统一事件队列：会引入类型擦除、调度复杂度和额外约束，偏离现有类型化 Channel 设计。

### D3: `EventChannel<T>` 向 `EventHub` 暴露最小调度回调，而不是让 Hub 轮询状态

**选择**：在 Channel 与 Hub 之间建立轻量调度协作：
- 首次 `Enqueue` 使空队列变为非空时，通知 Hub 标记该 Channel 为活跃。
- `Flush()` 把队列消费完后，通知 Hub 将该 Channel 从活跃集合移除。
- 仅执行同步 `Publish` 的 Channel 不进入活跃集合。

**理由**：
- 让 Hub 从“拉模式轮询”变成“推模式激活”，避免空检查成为常规成本。
- 激活/移除可以设计成 O(1)，非常适合事件频率高但同时活跃通道数少的场景。

**替代方案**：
- 每帧查询 `PendingCount`：实现简单，但仍有轮询成本。
- 拆分 `AsyncEventChannel<T>` 与 `SyncEventChannel<T>` 两种类型：语义更清晰，但会导致业务 API 和代码生成变化更大。

### D4: 调试可视化从“实例枚举”升级为“声明槽位 + 实例状态”视图

**选择**：Editor 监视面板不再假定“所有声明的 Channel 都已有实例”。生成代码或运行时元数据需要支持以下状态：
- 已声明但未创建
- 已创建但空闲
- 已创建且活跃

**理由**：
- 延迟创建后，如果仍靠“遍历实例”展示，会导致未初始化事件在面板中不可见，调试体验下降。
- 用声明槽位描述所有事件，再附加实例状态，可以同时满足懒加载与可观察性。

**替代方案**：
- 打开面板时强制创建全部 Channel：这会直接破坏延迟创建的目标。
- 面板只展示已实例化 Channel：对定位“为什么某个事件从未初始化”帮助有限。

### D5: `Shutdown()` 仅清理已创建 Channel，并重置活跃集合

**选择**：`EventHub.Shutdown()` 只遍历已创建的 Channel 实例进行 `Clear()`，并清空活跃集合与相关索引状态。

**理由**：
- 未创建的 Channel 本身没有资源需要释放。
- 与延迟实例化模型一致，不需要维护一个永远完整的 `_allChannels` 数组。

**替代方案**：
- 为所有声明槽位补一个虚拟 `Clear()` 调用：无实际收益，还会让结构变复杂。

## Risks / Trade-offs

- **[Risk] 活跃集合维护增加状态同步复杂度** → 通过“仅在空→非空、非空→空两个边界切换时通知”降低重复登记和漏删概率，并补充边界测试。
- **[Risk] 延迟创建会改变某些调试假设** → 明确把“未创建”作为合法状态纳入监视面板展示，而不是把它当异常。
- **[Risk] 生成代码、运行时接口、编辑器面板会同时变更** → 先保持对外业务 API 稳定，把改动限制在代码生成器和事件基础设施内部。
- **[Trade-off] 为了 O(1) 激活/移除，Channel 可能需要额外持有调度索引或激活标志** → 增加少量状态字段，换取帧级扫描成本的大幅下降。
- **[Trade-off] 同步事件是否应在面板中标记为“从未参与异步调度”需要额外状态定义** → 在规格中把“已创建但无待处理异步事件”定义为通用空闲态，避免面板概念过细。

## Migration Plan

1. 扩展 `EventChannel<T>` 与相关接口，使其支持与 Hub 的活跃调度协作。
2. 更新 `EventCodeGenGenerator`，生成延迟创建属性、活跃集合管理和调试元数据访问结构。
3. 重新生成 `EventHub.Generated.cs`，确保现有业务调用点无需改签名即可继续编译。
4. 更新事件监视面板，使其能展示未创建/空闲/活跃三类状态。
5. 用现有 `SceneEnter`、`BeforeSceneEnter` 等异步事件验证激活/移除行为，并用仅同步发布的事件验证其不会进入刷新集合。
6. 如设计不满足预期，可通过重新生成回退到“全量初始化 + 全量遍历”的旧结构，回退面较集中。

## Open Questions

- 监视面板是否需要显式显示“延迟创建次数/首次访问时间”之类额外诊断字段？当前设计不是必须项。
- 对于“已创建但长期只有 `Subscribe/Publish`、从不 `Enqueue`”的 Channel，是否需要在调试面板中额外区分“同步专用”状态？当前可先不区分。
